3. Two Permission Layers

⬤ Layer 1 — Hasura Declarative Permissions (GraphQL Gateway)
All read/write access to the GraphQL API passes through row-level permission rules declared in the metadata. These rules are evaluated by Hasura before any SQL reaches Postgres, using the X-Hasura-User-Id session variable injected from the JWT. This layer enforces multi-tenant data isolation and basic role scope (all/member/owner+editor).
⬤ Layer 2 — Serverless Action Handlers (Side-Effect Authorization)
Three GraphQL Actions (triggerWorkflowRun, approveWorkflowStep, createOrganization) route to serverless functions. These functions use the Hasura Admin client to perform multi-table writes and enforce role requirements that go beyond data scoping — quota checks, owner-only operations, and approval-gate authorization — returning HTTP 403 when callers lack required roles.

3.2 Layer 1: Key Filter Expressions (from metadata)

organizations — SELECT filter

User sees only organizations they are a member of.

{ "organisation_members": { "user_id": { "_eq": "X-Hasura-User-Id" } } }
workflows — INSERT check (owner/editor gate)

Only owner or editor may create a workflow inside an organization.

{ "organization": { "organisation_members": { "_and": [ { "user_id": { "_eq": "X-Hasura-User-Id" } }, { "role": { "_in": ["owner", "editor"] } } ] } } }
workflows — DELETE filter (owner-only)

Only the org owner may delete a workflow (stronger than INSERT/UPDATE which allow editors too).

{ "organization": { "organisation_members": { "_and": [ { "user_id": { "_eq": "X-Hasura-User-Id" } }, { "role": { "_eq": "owner" } } ] } } }
workflow_run_steps — SELECT filter (4-hop traversal)

The deepest filter chain in the schema — traverses four relationships to scope step data to org membership.

{ "workflow_run": { "workflow": { "organization": { "organisation_members": { "user_id": { "_eq": "X-Hasura-User-Id" } } } } } }
workflow_runs — INSERT preset (auto-set fields)

Hasura auto-injects status and user_id on insert, preventing client-side manipulation.

columns allowed: [ "workflow_id", "input" ] preset: { "status": "pending", "user_id": "X-Hasura-User-Id" }
organization_members — UPDATE/DELETE filter (owner gate)

Managing members (adding/removing) requires the acting user to be an owner of that same organization.

{ "organization": { "organisation_members": { "role": { "_eq": "owner" }, "user_id": { "_eq": "X-Hasura-User-Id" } } } }

3.3 Layer 2: GraphQL Actions & Serverless Authorization

Three mutations bypass the declarative permission layer and are handled entirely in serverless functions, which use the Hasura Admin secret to read and write data free of row-level restrictions, while enforcing richer business rules in code.

createOrganization
Handler: /create-organization  |  Type: mutation · synchronous  |  Args: name: String!

Creates the organization row and inserts the caller as owner in organization_members in a single atomic operation. The admin client is required because Layer 1 does not allow users to self-assign the owner role.

triggerWorkflowRun
Handler: /trigger-workflow-run  |  Type: mutation · synchronous  |  Args: workflow_id: uuid!, input: jsonb

Validates membership (owner or editor), checks calls_used < max_quota, creates a pending run record, and then calls the /engine function to start step execution. Returns run_id immediately so the UI can open a subscription before execution finishes.

approveWorkflowStep
Handler: /approve-workflow-step  |  Type: mutation · synchronous  |  Args: step_run_id: uuid!, approved: Boolean!

Traverses the full relationship chain workflow_run_steps → workflow_runs → workflows → organizations → organisation_members to resolve membership. Guards: step type must be approval_gate, run status must be waiting_approval, caller must be owner or editor. On approval, writes audit fields (approved_by, approved_at) and resumes the engine from step_order + 1. On rejection, marks both step and run as failed.

Why Layer 2 is necessary for these three operations: Hasura row permissions operate on individual table rows. They cannot enforce cross-table business rules like quota checks, cannot atomically create two related rows with role enforcement, and cannot resume a stateful execution engine. These side-effects require admin-level multi-table writes with application logic, which is exactly what serverless Action handlers provide.

4. Auth Schema (Nhost-managed)

The auth schema is tracked in the metadata for relationship traversal from application tables but does not carry application-level Hasura permissions. Nhost Auth manages its own session enforcement via JWTs.

auth.users→ user_providers (array), user_roles (array), refresh_tokens (array), oauth2_auth_requests (array), oauth2_refresh_tokens (array), security_keys (array)

The auth.users.id field is the canonical identity anchor. It is referenced by organization_members.user_id, workflow_runs.user_id, workflow_run_steps.approved_by, and matched against the X-Hasura-User-Id session variable in every permission filter above.
